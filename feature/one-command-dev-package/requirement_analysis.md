# 统一开发工具与一键开发出包——需求分析

> 创建日期：2026-10-11
> 当前阶段：需求分析已确认。已确认范围和边界整合于本文，已按用户本轮指示补充构建、测试与版本维护子命令；版本禁止降级，并提供当前版本 patch 加 1 的显式自增能力；具体实现细节在技术设计阶段确定。
> 需求确认不等于批准实施；技术设计与开发计划参见相应文档。

## 概述

让新开发者 clone SeaSnail 仓库后，在仓库根目录执行一个命令，检查已有构建工具环境，满足要求后自动准备项目依赖，并从当前仓库源码生成可用于本地开发与内部测试的未签名 macOS 应用包。同时服务开发者和作为主要开发、编译参与者的不同 Agent 工具。正常流程无需开发者或 Agent 手动串联阶段；Agent 能从仓库入口发现工具、判断执行状态并准确交付结果。

工具进一步提供统一的检查、增量/全量编译、自动化测试、出包、版本维护与运行查询能力。默认开发出包仍可单命令完成，各子命令按明确职责独立使用，共享帮助、状态、错误分类和操作边界。

## 背景与问题

### 当前事实

- 默认开发目标是 macOS 13+、Apple Silicon，默认识别运行时是 Sherpa ONNX SenseVoice int8。
- 现有流程需要开发者分别执行工具检查、前端依赖安装、OpenAPI 类型生成、Sherpa 输入获取和统一出包命令。
- `scripts/doctor.py` 只检查环境，不安装缺失工具。
- `scripts/sherpa/fetch-inputs.py` 获取并校验固定源码、子模块、依赖归档和模型；`scripts/build.sh --package` 在本地输入具备后构建或复用运行时，编译应用并组装开发包。后者不会自动完成前者的完整下载工作。
- 原生识别制品固定 Apple clang、macOS SDK 和 CMake 版本，并校验最终文件大小与哈希；运行目标版本与构建机器要求不同。
- Swift 辅助程序、Rust 和前端分别有依赖管理流程；首次执行需要联网。
- 部分步骤拒绝覆盖已有输出或不匹配输入。发生中断或重复出包时，可能需要开发者判断临时目录和目标路径如何处理。
- 当前包是未签名开发包，包含开发用文件凭据 fallback 标记；不具备正式发行语义。

### 本次出包的观察

默认 Node 版本不符合要求、项目依赖与运行时输入缺失，均需要显式处理。按文档补齐锁定输入并从当前仓库源码构建后，已成功生成 App 与 ZIP，未修改项目源码和锁文件。原生编译与模型包重复解压校验是主要等待阶段。

该结果证明现有构建链路在本机满足条件时能够完成，尚不能证明全新机器的环境检查、项目依赖准备、中断恢复或不同机器兼容性已成立。

### 要解决的问题

新开发者需要理解多个工具、版本限制和命令顺序，容易在准备不完整时启动长时间构建；失败后又需要人工判断如何重试。若每次都由 Agent 找工具、拼接命令和清理临时状态，项目的开发出包能力就依赖额外协助。

用户进一步明确：后续软件开发和应用编译主要由 Agent 参与。新开发者可能使用不同 Agent 工具，因此出包能力还需要可发现、可理解且不绑定单一厂商。仅提供命令和面向人的日志，仍可能让 Agent 猜测执行状态、误判成功或盲目重试。

## 目标与成功标准

- **G1 单命令入口**：clone 后使用一个命令检查环境并生成未签名开发包；工具缺失或版本不符时先提示原因与解决方法，由用户处理后重跑。
- **G2 当前仓库构建**：缺失依赖按项目文档和锁定来源获取，不扫描其他项目目录、不借用其构建产物。
- **G3 自动执行**：正常路径由工具自行推进，开发者和 Agent 无需手动串联阶段或修补代码。
- **G4 最小启动条件**：文档明确能够启动该命令的最小系统条件；即使缺少后续阶段需要的工具，也应能输出必要的诊断或明确引导，不能因诊断入口自身缺依赖而无解释退出。
- **G5 可重复执行**：首次、中断后重跑和再次出包使用同一入口；仅复用符合当前版本与校验要求的输入和制品，保留已有成功产物。
- **G6 失败可诊断**：失败显示具体阶段、原因、日志位置和恢复操作，并返回非零结果；不得把不完整产物显示为成功。
- **G7 交付可检查**：成功时给出 App 路径及验证摘要；同时提供 ZIP、SHA-256 校验文件和构建记录。
- **G8 不削弱约束**：保持现有锁定来源、工具链和制品校验，以及许可证材料收集；不得因环境不足而更新锁定哈希或跳过检查。
- **G9 Agent 可理解性**：Agent 仅依赖公开文档、命令帮助和工具输出，就能判断能力、前置条件、执行状态、失败原因及允许的下一步动作，不需要阅读内部脚本或历史聊天记录。
- **G10 跨 Agent 工具发现**：工具入口由仓库携带，不依赖单一 Agent 厂商、专用插件或预装 skill；对明确支持的 Agent 提供发现指引，其他 Agent 可通过 README 引导使用。
- **G11 统一开发操作**：同一工具按子命令执行检查、构建、测试、出包、版本维护和状态查询，正常路径自动准备相应任务所需的依赖。
- **G12 操作边界可判断**：全量编译、测试和版本更新的范围与文件副作用公开；显式版本修改可预览、一致性校验和失败恢复，不被出包或重试隐式触发。

本阶段不承诺首次构建的固定时长。验收应记录下载、准备、编译和打包耗时；是否设定性能预算需根据实际基线另行决定。

## 用户与核心场景

### 场景 1：新开发者首次出包

前置条件：macOS Apple Silicon、已 clone 的完整仓库，以及执行诊断入口所需的系统基本能力。首次完整出包还需要可用网络、足够磁盘空间和检查通过的工具环境；诊断入口应尽量使用系统已有能力，缺少构建工具时仍能提示。具体最低构建系统版本与启动能力清单在技术设计阶段核实。

用户在仓库根目录执行一个命令。系统检查已有工具与系统条件，全部满足后安装项目依赖、获取并校验源码和模型、从源码构建并组装应用，显示产物与验证结果。无需在各阶段之间另行执行命令。

工具缺失、版本不符或系统条件不足时，在大量下载和编译前停止并给出具体原因与解决步骤。用户处理后重跑同一入口；出包脚本不自动安装或升级构建工具。

### 场景 2：已有工具不符合版本要求

开发者已有某些构建工具，但版本不符合仓库要求。系统识别差异，报告实际版本、要求版本及安装、升级或选择正确工具环境的方法。用户完成处理后重跑入口，检查通过才进入项目依赖准备和编译。

脚本保留原有工具与全局配置，不在仓库下载另一套工具，也不自动修改 shell 配置、全局工具版本或系统开发工具选择。修复工具环境是用户操作，工具提供指引。

### 场景 3：网络失败或用户中断后重跑

下载或编译未完成，开发者再次执行同一命令。系统区分已验证输入、未完成状态与用户修改，继续可以安全恢复的工作；失败内容不被误认作可复用制品。

可重试的临时网络失败与版本、哈希、源码状态错误应分别反馈。不能安全恢复时，说明阻塞项与处理方式，不自动删除未知内容。

### 场景 4：再次构建当前源码

当前仓库已有校验通过的依赖与运行时，开发者修改应用源码后再次执行入口。系统校验复用条件、构建当前代码并生成新产物，保留上一份成功包。

不承诺仅凭存在目录或完成标记就复用，也不承诺所有依赖在任何情况下均无需联网。

### 场景 5：Agent 从全新仓库发现并使用工具

新开发者使用支持清单内的 Agent 工具打开全新 clone，并提出生成开发包的任务。Agent 从仓库入口发现推荐命令，查看帮助和环境检查信息，执行完整流程，根据执行结果交付产物及验证结论。

会自动读取仓库指引的 Agent 应可直接获得入口；不自动读取的 Agent，允许开发者提示“按仓库 README 的开发出包说明操作”。无需安装专用插件或逐一解释内部命令。不承诺任意 Agent 在完全无引导时自动发现工具。

### 场景 6：Agent 判断失败与恢复边界

Agent 执行出包时遇到网络故障、系统条件不足或校验失败。工具提供可可靠识别的分类、当前状态、可重试性、恢复条件和日志位置。Agent 在授权范围内处理可恢复问题；需要系统交互或用户决策时，准确报告阻塞，不无限等待输入或盲目重试。

恢复后，Agent 使用同一入口继续。完成后报告本次实际检查范围，不能将出包成功描述为业务验收通过，也不能因为日志中出现局部成功就忽略整体失败。

### 场景 7：开发者选择构建与测试

开发者通过统一入口选择增量构建、全量构建或测试，无需自行串联依赖准备和底层命令。全量构建重新编译默认开发路径的全部构建目标，仍可使用校验通过的下载输入，不删除历史成功包或未知目录。

测试默认覆盖文档化的非交互自动化测试集，并允许选择单元测试、集成测试或全部已纳入范围的自动化测试。工具报告实际范围、通过、失败、跳过和未执行项；必需项缺失、失败或清理失败不能被算作通过。需要桌面交互、系统授权、真实账户或付费服务的验证，不因选择“全部”自动触发。

### 场景 8：显式更新应用版本

开发者或获授权的 Agent 查看版本、一致性检查、预览版本修改，或者显式选择按 patch/minor/major 递增及设定具体版本。工具只修改已声明的应用版本文件及必要的本地锁条目，保留其他修改；成功时各版本声明一致，失败或中断有恢复记录和操作指引。

构建、测试和出包不自动递增版本；版本更新不自动提交、打 tag、签名或发布。版本递增是有副作用的动作，成功后再次递增会产生新版本；Agent 在结果不明时应先查询，不能盲目重复执行。

## 术语

| 术语 | 含义 |
| --- | --- |
| 单命令 | 用户使用一个公开入口触发完整流程，内部允许执行多个阶段和子命令 |
| 工具环境 | Node、pnpm、Rust/Cargo、Python、CMake、jq、Apple 编译工具与 SDK 等；本需求只检查和提示，不自动安装 |
| 项目依赖准备 | 使用合格的已有工具，按锁文件安装包依赖并获取源码、模型、依赖归档及构建输入 |
| 最小启动条件 | 在执行环境诊断入口之前，机器必须已经具备的条件 |
| 当前仓库构建 | 应用源码及项目输入来自当前 checkout 和声明的上游，不依赖其他项目目录 |
| 锁定输入 | 仓库声明的版本、revision、大小、哈希或包管理器锁文件约束的依赖 |
| 开发包 | 当前项目定义的未签名 macOS `.app`，用于开发与内部测试 |
| Agent 可理解性 | 工具提供足够且明确的信息，使 Agent 无需猜测日志或阅读内部实现即可判断状态与操作边界 |
| 工具发现 | Agent 从仓库入口或开发者提供的 README 指引找到工具及使用说明 |
| 支持清单 | 明确验证过发现和使用流程的 Agent 工具范围；不代表所有 Agent 均自动读取同类文件 |
| 全量编译 | 不复用已有编译结果，重新编译默认路径全部目标；允许复用经校验的下载输入 |
| 默认测试集 | 文档中明确列出的无需人工交互的自动化测试范围，不等于完整业务或桌面验收 |
| 显式版本更新 | 按用户选定操作修改声明的应用版本文件，与构建、测试、出包分开执行 |
| 重跑恢复 | 再次使用同一入口，保留有效成果并处理流程自身产生的未完成状态；不要求进程级断点续执行 |

已确认边界：出包入口负责检查工具环境和提供解决指引；前端、Cargo、Swift 包依赖以及模型、源码等项目输入仍由统一流程准备；测试所需 Python 包属于项目依赖，仅使用已有解释器安装到受管理的项目依赖位置，不安装第二套 Python 或修改全局包环境。

## 功能需求

### FR-01 单一入口与启动检查

提供文档化的单命令入口。开发者无需提前掌握各构建步骤。入口应在大量下载和编译前检查平台、系统工具与 SDK 兼容性、写入条件和磁盘需求；列出实际检测结果、要求和阻塞项，并给出具体解决方法。工具环境不满足时不进入依赖下载或编译。

最小启动条件指运行入口并获得诊断所需的系统基本能力，不等于已经安装全部构建工具。入口尽量使用系统已有能力，缺少 Node、Python 等后续工具时仍应给出诊断或明确引导。

支持出包的平台沿用当前项目的 macOS Apple Silicon 范围，工具版本沿用仓库现有约束。App 的运行目标为 macOS 13+，不能据此推断所有 macOS 13+ 机器都可编译；具体最低构建系统版本及与固定 SDK 的兼容性须在技术设计阶段核实并写入文档。不符合条件时给出原因及解决方法，不放宽锁定工具链要求。

合法缺失且后续能够自动准备的项目依赖、源码、模型和归档应报告为待准备，不作为工具环境阻塞；已有输入损坏或漂移与工具缺失分别报告。命令名称、参数形式、具体检测方式留到技术设计决定。

### FR-02 工具环境检查与项目依赖准备

检查前端、Rust、Swift、识别运行时和 FFmpeg 出包链路所需的已有工具及版本，包含 Apple 工具与 SDK。缺失或版本不满足时，说明原因、实际值、要求值和可操作的解决方法，返回需用户处理的状态。

不自动安装、升级、替换构建工具，不在仓库安装另一套 Node、Python、Rust 等工具，不修改全局配置。用户修复后重跑同一入口。环境合格后，统一入口自动按锁文件安装前端、Cargo、Swift 包依赖，获取并校验模型、第三方源码和构建归档，并使用已有合格工具构建；这些属于项目输入准备，不属于工具安装。

不得依赖开发者已有的其他项目目录。通过检查的已有工具直接使用。标准包管理缓存的具体使用策略在技术设计阶段确定，并须满足锁定输入校验、保护用户已有内容以及不借用其他项目制品的约束。所有下载均使用声明来源及适用的完整性校验，不能关闭 TLS 校验。

### FR-03 从源码构建与完整组装

从当前仓库源码及锁定上游输入构建默认开发包。包含 GUI、daemon、原生辅助程序、默认 ASR 运行时、FFmpeg 和许可证材料；不能将缺少文件导入能力的冒烟包作为默认成功产物。

构建与出包不得自动改源码、协议、模型目录或依赖锁来绕过构建失败；显式版本维护仅允许 FR-15 声明的版本变更。兼容候选后端不属于默认路径。

### FR-04 重复执行、恢复与产物保护

识别可复用与不完整状态，仅使用验证有效的成果；自身产生的失败状态应能恢复或提供明确处理方法。保护用户修改和既有成功产物，避免重跑时因默认输出已存在而要求开发者重新研究出包参数。

断点下载、缓存布局、清理策略和并发行为属于后续设计事项，本阶段不锁定实现。

### FR-05 过程反馈与失败处理

提供明确阶段状态、持续可观察的进展和耗时信息；无法测量总体进度时，不显示虚假百分比。记录构建日志，成功或失败均输出位置。

对缺工具、系统条件不足、网络失败、空间不足、输入漂移、编译失败和许可证缺失分别给出可操作提示。任何失败阶段都不能被成功摘要掩盖。

### FR-06 交付与验证

成功前执行与出包相称的资源完整性、原生架构、App 元数据和许可证检查。成功摘要说明版本或源码身份、产物路径及开发包限制。

默认生成 App、ZIP、SHA-256 校验文件和构建记录。出包验证与完整业务验收分别报告，构建成功不能描述为完整业务测试通过。

### FR-07 文档与自主使用

新开发者从 README 或构建教程能够找到唯一推荐入口、最小条件、工具环境处理方法、项目依赖自动准备范围、失败恢复方式和产物位置。正常流程既可由开发者直接执行，也可由 Agent 执行；不依赖特定 Agent、历史聊天记录或维护者临时指导。

### FR-08 面向 Agent 的状态与结果理解

各子命令保留面向人的进度和诊断，同时提供机器可读的执行摘要与可区分的完成状态。Agent 应能可靠识别本次运行、源码身份、当前阶段、成功/失败/中断/需外部处理、产物位置、日志位置和验证范围，不以自然语言关键词匹配作为唯一依据。

失败信息应区分原因、可重试性、恢复条件与操作限制。说明哪些问题允许重试，哪些需要调查或用户决策；校验失败不能被建议为自动改锁、删未知目录或跳过检查。执行状态与最终结果保持一致，旧运行和并发运行的输出不能混淆。任务开始后应及时提供运行身份，并有只读方式发现当前及历史运行；最终输出丢失时，Agent 不必读取内部目录即可查询候选任务，但不能将最近一次运行直接认定为本次操作。

命令名称、结构化格式、字段、状态编码和兼容策略留到技术设计确定，本阶段不锁定接口实现。

### FR-09 非交互执行与权限边界

支持可预测的自动执行方式，明确网络、安装、文件变更和系统交互的范围。无法满足必须的输入、权限或外部条件时，返回清晰状态和恢复指引，不无限等待交互，也不绕过 Agent 工具自身的权限控制。

可恢复问题按授权范围继续；需要用户介入的事项必须与普通可重试失败区分。工具输出帮助 Agent 判断下一步，不赋予其额外修改源码、删除数据或变更系统的授权。

### FR-10 跨 Agent 的仓库发现入口

在根 README 提供显眼的工具入口，并通过根 `AGENTS.md` 提供简短的仓库操作指引。不同 Agent 是否自动读取该文件应以支持清单及实测为准，不能假定全部遵循同一发现机制。

维护一份统一的工具使用说明，覆盖用途、前置条件、帮助与环境检查方式、执行与交付、错误和恢复规则。仓库入口和适配指引引用该说明，避免复制多套参数或业务规则造成漂移。

首批支持 Codex 与 Claude Code，分别验证其仓库指引发现和调用流程。核心能力通过通用命令行开放；支持清单内的 Agent 可提供其能识别的轻量指引。专用 skill 或插件只能作为便利层，不是正常使用的前置条件。未自动发现入口时，开发者只需引导阅读 README，不必提供内部操作知识。

### FR-11 执行证据与准确交付

执行结果按任务区分构建证据、测试报告和版本变更清单，并关联源码身份、实际工具版本、依赖/制品校验身份、产物校验值及执行的检查范围，供人和 Agent 追溯。失败和中断同样保留足够诊断，避免仅成功时才有记录。

输出内容不得泄露凭据或应用账户数据。Agent 能区分本次有效产物、历史产物和未完成输出，并准确说明未执行检查及开发包限制。

### FR-12 统一子命令与任务范围

通过同一公开入口提供环境检查、构建、测试、出包、版本维护与运行查询；子命令提供各自帮助，并共享机器可读输出和错误约定。单命令完整出包能力保留，不要求用户先手动执行构建或测试。无效参数及不支持的组合在有副作用前拒绝。

各任务只检查和准备自身必需的环境与依赖；只读版本查询不能因为缺少原生编译工具而被阻塞。文档说明每个任务的输入、输出、网络需求、文件副作用和成功含义。

### FR-13 增量与全量编译

默认构建使用经验证的有效原生制品和构建工具增量能力，始终反映当前源码。全量构建重新编译默认开发路径全部目标，不跳过 Sherpa、FFmpeg、前端、Rust 或 Swift 目标；可以复用锁定且验证有效的下载输入。

全量编译不等于清空全部缓存。仅重建工具管理、归属明确的编译结果；保护用户文件、历史成功包与标准下载缓存。构建成功不等于已经交付 App/ZIP，也不等于测试通过。

### FR-14 一键自动化测试

提供默认测试集及可选择的单元、集成和全部自动化测试范围，接入现有前端、Rust 与 API 回归能力，并包含本工具自身测试；不顺带重建项目测试体系。自动准备所选范围必要的依赖、测试构建和本地原生制品，不要求先人工出包。

默认运行无需人工交互的单元与常规检查；集成测试接入既有本地 API 快速回归，“全部”包含既有完整自动化 API 验收。具体集合在设计中明确并跟随登记更新，不能依靠静态用例数量判断完整性。

测试报告关联本次源码、所选范围、实际执行项目、通过/失败/跳过/未执行、重试或 flaky、清理结果及下层报告路径。所选范围的必需项未通过、缺失、被跳过、flaky 或清理失败均返回非零。无人交互不等于无执行权限；条件不足时明确报告，不自动申请权限或调用真实付费 provider。

构建、出包校验、自动化测试和完整人工业务验收分别记录；出包不隐式承诺已运行全部测试。完整桌面人工验收、真实账户与付费服务评测保持后置。

### FR-15 显式版本维护与修改保护

支持查看、检查、预览、按 patch/minor/major 递增、当前版本自增及设置应用版本；MVP 采用普通三段式版本，不扩展预发布、发行编排或自动发布流程。只修改列明的应用版本声明，以及为保持依赖解析一致所必需的本地项目锁条目，不升级第三方依赖或改变工具链/模型哈希。

已确认禁止降级：设定版本不得低于任一已声明的有效应用版本；与当前一致的设定不产生版本变更。自增指普通三段式版本的 patch 加 1，例如 `1.2.3 → 1.2.4`、`1.2.9 → 1.2.10`，不修改应用构建号；存在版本冲突时先报告，不能猜测基准值。未提交事务失败后的安全回滚仅恢复操作前状态，不属于新版本设定；已提交更新不能借恢复机制降级。

查看、检查和预览保持只读；实际更新在仓库任务互斥下完成，事前列明当前值、目标值和文件清单，事后校验一致性。允许仓库有无关未提交修改，但必须保留它们；遇到版本冲突、无法验证的改动或未完成事务时明确报告。

多文件更新失败或中断不能被报告成功；提供可恢复事务证据，恢复时不得覆盖用户后续修改。构建、测试和出包遇到未恢复的版本事务应阻塞，避免使用混合版本。版本成功更新后再执行递增是新的动作，不宣称盲目重试具有幂等性。

版本更新不自动提交、不打 tag、不推送、不签名、不更新所有独立组件版本。应用构建号的自动递增和独立组件发版不纳入本次范围。

## 非目标与后置项

- Developer ID 签名、公证、staple、公开发布、自动上传或安装到 Applications。
- Windows、Linux、Intel Mac 构建支持。
- 自动安装、升级或替换构建工具；在项目内额外安装工具链，修改 shell 配置或系统开发工具选择。
- 自动授权麦克风、辅助功能或创建用户账户；这些属于首次使用流程。
- 运行命令修改现有模型、第三方依赖解析、原生制品哈希或模型许可证要求；显式版本更新仅可同步必要本地项目版本锁条目。为修复 FFmpeg 的 macOS 13.0 部署目标，开发接入阶段允许提交对应 API 制品基线的受审更新及验证证据，不放宽质量规则、预算或模型/Sherpa 哈希。
- 自动提交、打 tag、推送、发行发布，自动递增应用构建号及独立组件发版。
- 新建完整测试体系、自动运行人工桌面验收或付费 provider 评测。
- 默认使用其他目录或远端预编译 ASR 制品替代当前源码构建。
- 云端构建服务、CI 平台改造、离线首装包和多个 ASR 后端的一键准备。
- 承诺任意 macOS 机器无交互成功，或承诺固定首次构建时长。
- 承诺任意 Agent 在完全无引导时自动发现工具，或建设所有 Agent 厂商的插件、MCP 服务和专用 skill。
- 通过工具输出指令扩大 Agent 权限、绕过审批，或自动修补源码与锁定规则。

上述非目标为本次已确认边界；后续扩大范围需先调整需求和验收。

## 约束与风险

| 项目 | 事实或风险 | 需求边界与应对要求 |
| --- | --- | --- |
| Apple 工具与 SDK | 安装受系统兼容性、供应方和权限约束，App 运行目标不能替代编译条件 | 沿用当前 macOS Apple Silicon 范围与仓库工具约束，设计阶段核实最低构建系统版本；仅检查和提示 |
| 二进制可复现性 | 源码版本相同不保证满足固定制品哈希 | 提前校验工具链，保持产物校验，失败不得自动更新基线 |
| 引导工具依赖 | 当前检查和获取流程依赖 Python 等工具 | 入口尽量使用系统已有能力；缺少后续构建工具也能提示，具体启动清单在设计阶段核实 |
| 网络与上游可用性 | 多个依赖来源，首次需要联网 | 可观察、可重试；校验失败停止，不静默替换来源或内容 |
| 下载与编译资源 | 首次原生编译耗时，需磁盘和内存 | 提前检查并记录耗时，具体预算由设计与验证确定 |
| 全局环境影响 | 修改工具和 shell 配置可能影响其他项目 | 仅检查工具环境；不自动安装工具或修改全局配置 |
| 失败恢复 | 临时输入可能与用户修改混在一起 | 仅处理可识别的本流程状态，保护未知内容 |
| 凭据与隐私 | 构建日志及进程环境可能含敏感信息 | 不读取应用账户数据、不记录凭据；保留开发包限制说明 |
| Agent 发现差异 | 不同工具读取仓库指引的机制不同且可能变化 | 统一事实来源、README 兜底，声明并实测支持清单 |
| 文档与接口漂移 | 多个入口复制规则可能不一致 | 简短入口引用统一说明，帮助、文档和执行行为一致 |
| 状态误判 | 混杂日志、局部成功和旧输出易被误读 | 提供可靠执行状态和本次证据，区分运行与产物 |
| 多任务副作用 | 全量构建、测试和版本维护具有不同写入范围 | 公开任务边界并互斥共享资源，版本事务异常不能污染后续构建 |
| 版本更新重试 | 多文件更新无法依靠一次文件写入保证整体一致，递增成功后重跑会再次递增 | 预览、事务证据、冲突保护和恢复；结果不明先查询 |
| 测试完整性 | 部分绿色结果、skip 或 flaky 容易被误述为整体通过 | 按本次所选必需范围聚合，保留下层报告和清理结果 |
| 自动执行与权限 | Agent 环境可能限制网络、系统交互或文件写入 | 明确外部处理条件，不承诺工具能绕过执行环境限制 |
| 模型与第三方条款 | 开发出包不等于模型再分发获准 | 保留材料收集与开发用途标识，不扩大公开分发承诺 |

| AC-14 | 自动执行缺少必需交互条件，或已有其他构建占用相关资源 | 返回可识别状态和操作指引，不无限等待输入、不混淆运行及结果 | FR-04、08、09 |

| AC-16 | 核对仓库入口、统一说明、命令帮助及支持清单 | 推荐命令与规则一致；工具使用不要求厂商专用插件，适配入口不复制独立业务规则 | FR-07、10 |
| AC-17 | 符合文档最小启动条件，但缺少后续构建工具；另在不满足构建平台或 SDK 条件的场景执行 | 入口能够诊断并提示解决方法；支持范围和最低构建条件与文档一致，不把 macOS 13+ 的 App 运行要求当作通用编译承诺 | FR-01、02、07 |
| AC-18 | 查看子命令帮助，执行无效参数；缺原生工具时查询版本 | 帮助与边界明确，无效输入无副作用；只读版本操作不要求完整构建环境 | FR-12、15 |
| AC-19 | 已有编译结果和旧成功包，执行全量编译 | 全部默认构建目标重新编译；有效下载输入可复用；不删除未知内容或旧交付 | FR-04、13 |
| AC-20 | 无测试依赖和测试构建，执行默认/单元测试 | 自动准备必要依赖，执行声明默认范围；报告测试范围与结果，不要求先手动出包 | FR-02、12、14 |
| AC-21 | 分别选择集成与全部自动化测试 | 自动准备当前仓库所需运行时并接入既有 API quick/acceptance；不借用旧包，不调用付费 provider，不要求桌面授权 | FR-02、14 |
| AC-22 | 测试出现失败、必需项跳过/缺失、flaky、清理失败或条件不足 | 非零退出，保留实际范围及下层报告；不宣称所选测试集通过 | FR-05、08、11、14 |
| AC-23 | 查看/检查/预览版本，再显式递增或设置版本 | 只读操作不改文件；实际更新仅改声明版本与必要本地锁条目；保持第三方依赖和无关修改；不提交或打 tag | FR-12、15 |
| AC-24 | 版本原本冲突、更新途中失败/中断，或恢复前用户改动目标文件 | 不报告成功；按事务证据安全恢复或报告冲突；未恢复前构建/测试/出包不使用混合版本，不覆盖用户改动 | FR-04、08、15 |
| AC-25 | 连续构建/测试/出包，以及 Agent 查询一次结果不明的版本操作 | 普通任务不递增版本；版本恢复与新递增明确区分，Agent 不盲目重试有副作用动作 | FR-08、09、12、15 |
| AC-26 | 并发启动构建、测试、出包及版本更新 | 修改任务互斥且立即报告 busy；查询可用；运行、测试报告和版本事务不混淆 | FR-04、08、12～15 |
| AC-27 | 自增当前版本，预览自增，再尝试设置更低版本 | 自增仅将 patch 加 1；预览无修改；较低版本被拒绝且文件不变；已提交后新自增属于新动作 | FR-15 |
| AC-28 | 新 clone 的合法项目输入尚未下载，或已有输入哈希损坏 | 检查区分待准备与完整性错误；前者不要求用户手动准备，后者不改基线、不宣称可安全复用 | FR-01、02、08 |
| AC-29 | 在任务开始通知前后或版本提交后断连，随后通过公开接口查询 | 能发现当前/历史候选运行并读取提交状态；不盲选最近任务或重复递增；查询无写入 | FR-08、12、15 |
| AC-30 | 默认 Rust 测试缺少必需 FFmpeg，或存在未登记的隐式跳过/ignored 项 | 自动准备或明确阻塞；必需测试未执行不能计通过；真实 Keychain 等明确排除，不访问用户数据 | FR-14 |
| AC-31 | 检查出包中各 Mach-O 的运行目标，并在部署目标修复后执行冷构建与 API 回归 | 依赖不要求高于 macOS 13.0；修复配置经审阅，固定基线与新制品一致，运行命令不自动改基线 | FR-03、06、14 |
| AC-32 | 无 Cargo 依赖缓存的新 clone，执行版本检查或自增；注入 manifest/lock 不一致 | 版本操作不下载第三方依赖；结构校验识别不一致，变更只限白名单；不能以 no-deps metadata 的零退出证明一致 | FR-12、15 |

全新 clone 是必要条件；本机已有的项目产物不能替代首次准备验收。环境诊断验收应另有缺少工具和版本不符的隔离场景证据，验证原因、解决指引和不安装工具的边界；用户修复后重新执行同一入口应通过检查。项目依赖准备应在工具环境合格、且缺少项目输入的环境中独立验证。最小启动能力、最低构建系统版本和标准缓存策略的具体实现应在设计中明确；这些细节不得改变本文的平台范围、只检查不安装工具及输入校验边界。

跨 Agent 验收记录应明确工具及版本、仓库指引加载方式、初始任务提示、实际调用、执行结果与人工介入。测试环境的权限限制按实际报告；不能把维护者预先告知内部命令、手动修复或既有制品伪装为 Agent 自主完成。首批支持清单已确认为 Codex 与 Claude Code；具体测试版本和指引适配方式在设计阶段确定。
